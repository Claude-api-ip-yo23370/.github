<p>排查的顺序比工具重要。请求开始报错时，绝大多数人第一反应是换 IP，结果换了三条还没好，因为问题根本不在出口。这篇按故障树的思路走：先看症状落在哪一类，再顺着分支往下定位，每一层给一个能立刻执行的判断动作。试水阶段只拿一条也是这个逻辑，一条够用来验证，不够再补，不必一次押上整年的预算。</p>

<h2>一、先看症状，再往下找分支</h2>
<h3>把症状归成四类</h3>
<p>连续失败、偶发失败、延迟抖动、被要求验证。连续失败通常指向出口被拒或凭证失效；偶发失败多半是上行争抢或限流；延迟抖动看路由和同段邻居；被要求验证则要分是新号还是老号，两者的含义完全不同。归类花一分钟，能省掉几小时的乱试。</p>
<h3>第一件事永远是确认出口是不是你以为的那个</h3>
<p>用 curl 打一次 ipify 或 ifconfig.me，把返回的 IP 和你记录里的对一遍。看起来傻，但代理配置写错、环境变量没生效、客户端走了直连，这几种情况在实际排障里出现频率非常高。确认出口无误，再往下走分支。</p>

<h2>二、分支一：出口属性不合格</h2>
<h3>三项判定</h3>
<p>ipinfo.io 看 asn 与 org，是否本地运营商；ipapi.is 看 is_datacenter，是否为 false；再看 whois 的 country 与 city 是否与账号资料一致。三项里任意一项不过，先换线再谈其他。这一步不需要任何技巧，纯查表。</p>
<h3>换线之后的验证动作</h3>
<p>换了新出口，先用一条低强度请求跑二十次，看是否还会失败。如果仍然失败且返回码相同，说明问题不在出口，回到树根重新归类。这个「换一条再试」的动作最多做两次，两次无效就别再换了，成本已经够高。</p>

<p>试水阶段为什么只拿一条：一条出口足够验证「出口属性是否合格」这个分支，多了只是增加变量。确认这一层没问题，再决定要不要按号铺开。</p>

<h2>三、分支二：会话在漂移</h2>
<h3>表现是「时好时坏，没有规律」</h3>
<p>同一个号，上午正常，下午开始要求验证，第二天又好了。这类症状最典型的成因是出口在变：动态池子按请求轮换，一个号一分钟内可能落到三个城市。查法很简单，把同一个号连续十次请求的出口 IP 打印出来，如果有多个，问题就找到了。</p>
<h3>修法：把出口钉住</h3>
<p>给每个号绑定一条固定出口，至少在一天内不变。动态出口也不是不能用，但要按会话粘滞的方式配置，让同一个会话尽量复用同一条线路。粘滞时间设成十分钟到半小时比较合适，太短等于没粘，太长失去动态的意义。</p>
<h3>还有一种漂移不在出口</h3>
<p>客户端的时区、语言、UA 版本在两次请求之间变了，也会造成同样的症状。检查一下是不是升级了客户端、换了容器镜像、或者多个脚本共用了一个配置文件。这类问题排查起来比出口更费时，但一旦发现就很好修。</p>

<h2>四、分支三：并发与限速撞墙</h2>
<h3>怎么区分限流和出口问题</h3>
<p>看返回码和失败的时间分布。限流通常有明确的返回码，且失败集中在某个时间窗口内，降低频率后立刻恢复；出口问题则与频率无关，低频也会失败。两种情况的处理完全不同，别混着来。</p>
<h3>参数怎么调</h3>
<p>先把并发从当前值砍一半，观察十分钟。恢复说明是容量问题，再按每次加百分之二十五往上找拐点。同时给客户端加指数退避，初始间隔一秒、上限三十秒、最多重试三次，这个配置能挡住大部分瞬时抖动。</p>
<h3>什么时候该加线路而不是降并发</h3>
<p>如果业务本身需要这个并发量，降下来就失去意义，那就按号分摊：一个号一条出口，把总并发拆到多条上。这也是单账号独享出口的真实价值，它买的是并发上限的可预期性，不是单纯的「干净」。</p>

<h2>五、分支四：账号自身状态问题</h2>
<h3>换出口也救不回来的情况</h3>
<p>账号已经被要求补充信息、订阅状态异常、或者历史行为留下记录，这些换多少条出口都没用。判断方法是拿一个全新的测试号走同一条出口，如果新号正常、老号异常，问题就在账号侧。</p>
<p>这一步的意义在于及时止损。见过太多人在这棵树上绕了两天，最后发现是账号本身的状态问题，白买了三条线路。先做这个对照，能省下大量无效支出。</p>

<h2>常见问答</h2>
<h3>试水只买一条出口够用吗？</h3>
<p>答：验证阶段够用。一条能确认出口属性、会话稳定性和基本并发能力，这三项过了再按号铺开，比一上来买十条更省钱也更清楚。</p>
<h3>换了三条出口都没好，还要继续换吗？</h3>
<p>答：不要。三次同结果基本可以排除出口因素，继续换只是把成本转移到供应商身上，问题还在原地。</p>
<h3>退避参数设多少合适？</h3>
<p>答：初始一秒、上限三十秒、最多三次是通用起点。业务对延迟敏感就缩短上限，对成功率敏感就放宽次数。</p>
<h3>怎么判断是限流还是被拒？</h3>
<p>答：降频后恢复的是限流，降频后照样失败的是被拒。这个测试五分钟能做完，比猜快得多。</p>
